## 条件与性能口径

STM32 保留同一份 64 KiB fixture，SHA256 `2a65c721fa1be9c4fcddba2a32bb96ccaeece439b517adb167f00ea928c031a4`。10 个动态 32-bit 字段位于 `0x20000100+i*64`，每个字段高 8 位标识字段编号；采样脚本逐帧核对编号、完整 bitmap、CRC、探针时间和序号。共存模式增加前四字段的 Watch（100 ms）和 RTT（5 ms 检查）。

每档五轮，每轮约 5 秒，交替先测独立/共存，避免固定先后顺序。有效 Hz 按探针首末时间计算，PC 收包批次不作采样时刻。完整数值、文件身份及原始日志 SHA256 见 [机器可读结果](subscription-performance-20261015.json)。这不是无线链路或 SWD 硬件的理论极限。

## 10 字段无线 Timeline

最终静态读取块为 8 字段；控制可在块之间插入。所有 30 轮均没有 SWD 错误、partial 样本、板端 ring_dropped 或消费者游标缺口。

| 请求周期 | 单独运行：中位 Hz（五轮范围） | Watch + RTT 共存：中位 Hz（五轮范围） |
| --- | --- | --- |
| 2000 us / 500 Hz | 500.00（500.00–500.00） | 499.81（499.61–500.00） |
| 1000 us / 1000 Hz | 941.91（931.85–943.60） | 834.28（832.00–851.99） |
| 200 us / 5000 Hz | 1173.43（1170.58–1175.89） | 1050.64（1044.74–1054.98） |

更高请求频率不保证按周期执行。实时模式将来不及执行的时槽记为 sequence 跳号和 deadline_missed，继续输出完整样本；执行跨度超过请求周期带 budget_overrun 标记。上表高频档有这些缺口和超限，不能标成“无丢样的 5 kHz”。严格 deadline 模式可在超限后暂停。

扩块前同条件 4 字段块的 40 轮记录保留：100 Hz 基本跟随；500 Hz 为 500.00/499.81；1 kHz 为 935.64/783.51；5 kHz 请求为 1121.55/1020.64（单独/共存）。8 字段块对该目标的改善有限，共存 1 kHz 档约提升 6.5%，未解决全部调度与 SWD 开销。

## STM32 → ESP32 本地读取

不逐次经过 PC 往返，由 ESP32 本地执行并计时；每次命令上限约 500 ms，因此离散基准可能未完成请求的 10000 次读取。

| 地址模式 | 完成 word 数 / 探针用时 | 有效数据吞吐 |
| --- | --- | --- |
| 连续 32-bit / 8 word 块 | 10000 / 357188 us | 109.36 KiB/s（约 112.0 kB/s） |
| 64 B 间隔离散字段 / 8 word 组 | 7190 / 500017 us | 56.17 KiB/s（约 57.52 kB/s） |

这是当前实现的局部吞吐测量，未排除所有 ESP32 调度开销，不是电气接口上限。10 字段约 1173 帧/s 对应约 46.94 kB/s 的变量净数据、112.65 kB/s 的 RML1 帧。历史纯 TCP 连续回传约 0.726 MB/s，明显高于本次变量净数据率；优先优化地址访问、SWD 和调度有依据，不能只提高 Wi-Fi 带宽。

同次主机 API 对 10 地址批量轮询中位约 16.13 Hz，包含本地 HTTP 及控制屏障的多次 Wi-Fi 往返；这不是 Orbit/J-Link 的实测基线。订阅不再为每一帧等待 PC 请求，但实际 Orbit 调试适配器还有状态监控与调试控制开销。

## 0.2.4：状态监控、持续录制与有线目标

## Orbit同组十变量闭环

后续在隔离Orbit工作树修正了GCC多维数组解析：原解析器对同一个array DIE下的各subrange取最大count，丢失10×16的维度；现在按顺序建嵌套数组并计算64 B行跨度。检查动态/未知维度、各维度越界和整数溢出；采样引擎、Flash和目标fixture沿用同一份。76文件/1055项测试通过，类型检查和构建通过。

相同十个 `capture_values[i][0]` 离散变量、Watch前四字段、RTT和真实Orbit监控同时运行，三档各五轮、每轮5秒：请求500 Hz实际中位499.999 Hz（499.808–500.000）；请求1 kHz实际847.87 Hz（792.98–855.41）；请求5 kHz实际1057.96 Hz（1055.82–1063.93）。逐字段值标识核对通过，主机逐样轮询次数0。结构化记录见 [同组变量验收](orbit-matrix-acceptance-024.json)。

这一结果补齐了真实表达式→服务订阅→ESP32→STM32→Orbit事件的闭环，但10字段1 kHz持续目标和高负载共存下降≤5%的目标仍未达标。下一步优先拆分RTT单次执行的大块访问，测量它对Timeline调度的影响；不把本次集成通过写成性能全部达标。

## 0.2.5：RTT分步执行及真实断连

RTT的一轮改为控制块、描述符、每次最多16 B数据、RdOff提交几个步骤，每步后返回同一个执行器调度点。Timeline/控制可在步骤之间插入；控制屏障或显式暂停后重读描述符。保留待确认RdOff、数据和缓冲身份，恢复时核对已完成/未完成，不盲目重复写入。采集C模型新增执行块读取上限、Timeline/屏障插入、环绕及“写入完成但响应丢失”恢复，全部通过。

同组十变量+Watch4+RTT+真实Orbit监控，请求1 kHz的五轮各5秒实际为938.98–944.54 Hz，中位940.27 Hz，相比0.2.4的847.87 Hz约提高10.9%。仍未达到持续完整1 kHz。真实严格录制/超载显式恢复、RTT载荷校验与原生USB三订阅回归通过。

采集时用原生USB `80/05`仅断开探针STA、保留电脑热点：旧会话约2397.86 ms失败，自动恢复连接/虚拟设备约2942.02 ms。旧录制保留515帧并以session_closed失败封存；旧租约恢复后仍503、新会话不存在旧订阅，显式新建订阅才开始采集，旧文件哈希不再变化。目标counter继续增长、最终owner为空，未自动重放目标操作。这是设备主动STA断连测试，不替代电脑热点关闭或完整掉电。

73项主机测试通过，新增独立EXE离线inspect-recording、异常JSON/磁盘fsync失败处理和Python丢失会话close清理。fsync失败时尽力移除已写尾部、状态finalized=false；若存储连截断也失败，会报告invalidation_error，不能仅凭文件中的旧尾部判定运行成功。独立EXE在连接服务停止时成功校验12065帧文件，SHA256与录制结果一致。

同版本虚拟USB完整烧录/调试及pyOCD通过；64 KiB编程/校验本轮7105.70 ms，哈希和选项字节核对通过。它与此前5.51秒的差异保留为实际网络/主机条件下的功能验收计时，不作为新的烧录加速对照。具体身份和所有原始证据见 [0.2.5检查点](subscription-checkpoint-025.json)。

## 0.2.6：多重指针分批读取

每帧从根地址重新解析，复用本帧已经读取的共享指针／叶子字；每次 SWD 执行最多读取八个物理字，然后返回统一执行器的调度点。连续地址走块读，离散地址在一个 DAP 请求中逐项设置 TAR；不保留跨帧指针缓存，不在失败时自动重放可能已完成的操作。最大缓存扩至 160 个字，覆盖 32 字段各四级指针及一个叶子字。板端、服务和 SDK 的现有协议未改变。

### 498.51 → 958.04 Hz 的实际条件

这组是实际 Orbit `dist/debugadapter.js` 子进程，经公共 SDK／连接服务、电脑 2.4 GHz 热点、RMLink 和 SWD 访问运行中的 STM32F103C8；未包含已安装 VS Code 的界面渲染。请求 SWD 4000 kHz、采样周期 1000 us，CPU0 执行 SWD。前后保留同一目标 Flash 和 Orbit 工作树；主机服务版本标签由 0.2.5 改为 0.2.6，没有对应的主机采样算法改动。
